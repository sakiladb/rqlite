# CLAUDE.md

Maintainer guide for **`sakiladb/rqlite`** — an [rqlite](https://rqlite.io) Docker image preloaded
with the [Sakila](https://dev.mysql.com/doc/sakila/en/) sample database (via
[jOOQ](https://www.jooq.org/sakila)), published to
[Docker Hub](https://hub.docker.com/r/sakiladb/rqlite).

> One of the [`sakiladb`](https://github.com/sakiladb) image family (`postgres`, `mysql`,
> `sqlserver`, `oracle`, `clickhouse`, `rqlite`). The **reference template** for the family —
> the shared release machinery, the porting checklist, and the canonical prose — lives in
> [`sakiladb/postgres`](https://github.com/sakiladb/postgres) (its `CLAUDE.md`). This file
> documents only what is **rqlite-specific**. The org landing page is rendered from the
> [`sakiladb/.github`](https://github.com/sakiladb/.github) repo.

## Purpose

These images exist primarily as **test fixtures for the [`sq`](https://github.com/neilotoole/sq)
CLI**. `sq`'s suite asserts a uniform Sakila schema across every variant — the **same object set:
16 tables + 7 views** — so each image must expose that set. Treat it as a hard consistency contract:
a schema change here is a **cross-repo change** and `sq`'s expectations
(`testh/sakila/sakila.go`, `libsq/driver/driver_test.go`, `cli/cmd_inspect_test.go`) must be updated
in lockstep.

## The dataset

rqlite **is distributed SQLite**, so this variant is sqlite-derived: the dataset is a single SQLite
database, [`sakila.db`](sakila.db), baked into the image and served over rqlite's HTTP API. **16
tables + 7 views**, owned by `sakila`. Two family-parity points:

- **`film_text` is a plain table** (populated from `film`). SQLite full-text search (FTS5) requires
  a **virtual/shadow table**, which is schema-visible and would push the table count past 16. So,
  like the `sqlite`/`duckdb`/`oracle` variants, rqlite keeps `film_text` plain — structural parity,
  not a working full-text index. (Invisible-index FTS is only available on pg/my/sqlserver/clickhouse.)
- **Deterministic aggregating views.** `film_list`, `nicer_but_slower_film_list`, and `actor_info`
  collapse their actor/title lists with `group_concat(... ORDER BY ...)` (requires SQLite ≥ 3.44).
  The explicit `ORDER BY` makes their output **byte-identical** to the other variants. Verified:
  `film_list` / `nicer` / `actor_info` and the row data behind `customer_list` / `staff_list` are
  byte-for-byte equal to `sakiladb/postgres`.

> **Known SQLite-family difference:** the `sales_by_film_category` / `sales_by_store` views `SUM` a
> `DECIMAL` column. SQLite evaluates that in floating point, so the totals format differently from
> the `NUMERIC`-exact engines (e.g. `4656.3` / `33726.770000000004` vs pg's `4656.30` / `33726.77`).
> This is intrinsic to SQLite and is **shared identically by the `sqlite` and `duckdb` fixtures**, so
> rqlite stays consistent with its sub-family rather than matching pg here.

The dataset is regenerated by **`tools/regenerate-sakila.sh`** — it holds the canonical schema as
embedded DDL, copies row data verbatim from the previous `sakila.db` (so the original `last_update`
timestamps are preserved), then creates indexes/triggers/views and verifies (FK + integrity checks,
row-count parity vs source, `film_text` = `film`, and the expected 7-view set). It needs SQLite
≥ 3.44; point `SQLITE3` at a newer binary if your default is older:

```bash
SQLITE3=/opt/homebrew/opt/sqlite/bin/sqlite3 tools/regenerate-sakila.sh
```

## How the image is built

*(rqlite-specific.)* `Dockerfile` is a two-stage build that **bakes the data dir at build time** so
there is no seed cost at container start.

1. **`builder` stage** — pinned to `$BUILDPLATFORM` (the bake must run natively; under QEMU
   user-mode emulation `rqlited` reports ready but then fails to serve after `/boot`, which silently
   shipped an empty image as gh#8). It boots a fresh node, seeds `sakila.db` via the `/boot`
   endpoint, verifies the **running** node, then — the crucial gate — restarts a **brand-new**
   `rqlited` from the persisted dir and re-verifies, so an empty/incomplete bake fails the build
   instead of being published. This logic lives in `tools/bake.sh` (`set -eu`; a script, not an
   inline `RUN` chain, because the old `&& … || true` chain swallowed verify failures).
2. **final stage** — copies the baked `/staging/sakila-data` into `/var/lib/sakiladb/data` and
   points `DATA_DIR` there. The data dir is deliberately **outside the inherited `VOLUME /rqlite/file`**:
   BuildKit discards `COPY`/`RUN` writes under a `VOLUME` path (the source of gh#8's empty image), so
   the image bypasses the inherited volume entirely.

The baked data dir is architecture-independent (SQLite db + little-endian/4K-page BoltDB raft files),
so it is baked once on the native builder and `COPY`ed into both `linux/amd64` and `linux/arm64`.

### Readiness (HEALTHCHECK)

The final stage declares a Docker `HEALTHCHECK` that probes rqlite's unauthenticated `/readyz`
endpoint with `wget` (busybox wget ships in the base image; the `"*"` user in `auth.json` holds the
`ready` perm). The container reports `healthy` once the node is ready to serve. This matches the
family convention (every variant declares a `HEALTHCHECK` using its engine's native readiness probe).

## How releases work

*(Shared across the family — see `sakiladb/postgres` `CLAUDE.md` for the full description.)* Releases
are **tag-driven**: `.github/workflows/docker-publish.yml` builds on every push / PR / tag but only
**pushes on a `v*.*.*` tag**. The Docker tag is the major (`type=semver,pattern={{major}}` → `10`),
built multi-arch (`linux/amd64,linux/arm64`), pushed to **both Docker Hub and GHCR**
(`ghcr.io/sakiladb/rqlite`), and cosign-signed. rqlite currently has a **single major (`10`)**, so
`latest` (emitted by `docker/metadata-action`'s default `latest=auto`) always tracks it — no
`LATEST_MAJOR` gating is needed here yet (unlike `postgres`/`mysql`, which gate `latest` on a
`LATEST_MAJOR` env var because they publish several majors).

The git tag is `v{RQLITE_MAJOR}.{MINOR}.{PATCH}` — the major tracks rqlite's upstream major
(`ARG RQLITE_VERSION` in the `Dockerfile`, currently `10.2.0`); the minor/patch track sakiladb's own
revisions (in practice only the patch moves). To republish, bump to the next unused patch
(`git tag -l 'v10.*'` first) and push the tag:

```bash
git tag v10.0.7 && git push origin v10.0.7   # builds & publishes `10` + `latest`
```

> **First GHCR publish:** GHCR was added to the workflow on top of `v10.0.7` (which had shipped to
> Docker Hub only). The `ghcr.io/sakiladb/rqlite` package is created by the first tag build that runs
> with the GHCR target; a new GHCR package defaults to **private**, so set its visibility to public
> once (GitHub ▸ the package ▸ Package settings) — thereafter every tagged release pushes both
> registries automatically.

## Conventions

- **Credentials:** database / user / password = `sakila` / `sakila` / `p_ssW0rd` (in `auth.json`).
- **Ports:** `4001` (HTTP API), `4002` (Raft). Run with `--add-host rqlite1:127.0.0.1` so the baked
  advertise hostname resolves.
- **Tags:** Docker tag is the major (`10`); `latest` tracks it. Git tags are `v10.0.x`.
- **No AI attribution** in commits, tags, PRs, or any other content.
